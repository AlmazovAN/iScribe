# PR-30 — Аппаратная приёмка iScribe

**Состояние на момент создания PR:** аппаратные испытания не проводились. GitHub Actions выполняет синтетические тесты с имитацией Whisper. Ни один аппаратный критерий не должен получать статус PASS из-за этих тестов.

## 1. Что добавлено в приложение

Внизу страницы расположен сворачиваемый раздел **«Аппаратная приёмка · Не подтверждена»**. Он содержит семь контрольных проверок и кнопку **«Скачать протокол наблюдений JSON»** для выбранного файла. Кнопка доступна только вне активной обработки.

Перед выгрузкой приложение заново читает из IndexedDB исходный файл, запись задания и все сохранённые сегменты. Сравнивает с текущим состоянием количество и содержание сегментов и номер подтверждённого окна. В протоколе указывает:

- хеш коммита собранной версии, если `.git` доступен при сборке (иначе `unavailable`);
- модель, язык, длительность и размер в байтах;
- наличие исходного файла в IndexedDB, совпадение его размера и сохранённых контрольных точек;
- число ASR-сегментов, количество пропущенных меток говорящих и длительность покрытия;
- накопленные числа восстановлений и повторных запусков;
- фактически зарегистрированные типизированные события GPU → WASM, если они попали в ограниченный журнал;
- статус `HARDWARE ACCEPTANCE NOT VERIFIED` и **`NOT TESTED` для всех семи аппаратных критериев**.

JSON намеренно не содержит имени аудиофайла, текста, имен/ID говорящих, исходного аудио, произвольных сообщений ошибок, путей, полного user-agent или GPU-идентификатора. Числовая проверка успешно завершённой записи не доказывает, что модель, исходный файл и оборудование были настоящими: аналогичное состояние может создать тестовая заглушка.

Для окончательной приёмки необходим **реальный запуск на целевом устройстве и ручная фиксация результатов**. Ни GitHub CI, ни выгрузка JSON сами этого не делают.

## 2. Подготовка тестового места

1. Использовать **обычную производственную страницу React**, а не тестовый адрес `/tests/e2e/harness.html`. Последний использует подмену Whisper и не подходит.
2. После слияния PR-21–30 в `main` развернуть проверяемую сборку по согласованной процедуре. До этого можно тестировать локальный production-build или отдельный staging-адрес. Не подменять рабочий адрес без проверки миграции IndexedDB v2.
3. В записанный протокол занести: дату, SHA проверяемой сборки, Windows/Linux, версию Chrome/Edge/Opera, процессор, модель видеокарты, объём RAM, доступность WebGPU, режим питания. Сами эти идентификаторы не собираются приложением.
4. Держать исходный MP3 14 мин 31 сек / около 33,3 МБ **только локально**. Не загружать на GitHub, в публичные CI-artifacts или сторонние сайты.
5. Подготовить минимум две копии исходной записи как независимые задания для проверок полной обработки и возобновления. Не очищать данные сайта между попытками восстановления.
6. Убедиться, что отображается Whisper Small, язык `ru`, и предварительно сохранены необходимые веса. Первую проверку проводить **без диаризации**, затем отдельно — с ней.

**Базовый состав приложений к акту приёмки:** обезличенный `iscribe_hardware_evidence_*.json`, `iscribe_benchmark_*.json`, `iscribe_diagnostics_*.json` (при ошибках), локальные TXT для проверки полноты, заполненный ручной протокол. Исходное аудио и TXT не публиковать.

Порог производительности нельзя придумывать до измерения базовой конфигурации. Для HW-6 дополнительно фиксировать наличие памяти и нагрузку непосредственно перед запуском и после него. Если файл изначально повреждён, это фиксируется как отдельный отказ декодирования, а не как ошибка WebGPU.

Заполнить после фактического выполнения (подставить дату, устройства, путь к локально хранящемуся отчёту). Статус допускается только `PASS`, `FAIL`, `NOT TESTED`, `BLOCKED`.

| --- | --- | --- |
| HW-1 | NOT TESTED | — |
| HW-2 | NOT TESTED | — |
| HW-3 | NOT TESTED | — |
| HW-4 | NOT TESTED | — |
| HW-5 | NOT TESTED | — |
| HW-6 | NOT TESTED | — |
| HW-7 | NOT TESTED | — |

Критерий перехода к рабочей публикации: **настоящие HW-1 и HW-2 пройдены** и проверены отсутствие потери TXT/чекпоинтов, доступность модели на целевом устройстве, безопасность миграции IndexedDB, а для обещаний офлайн/диаризации/GPU-fallback — соответствующие HW-3–5. Если функциональность не прошла gate, её необходимо прямо обозначить как экспериментальную, а не включать в маркетинговые обещания.

## 5. Технические ограничения автоматической проверки

- Чистые Vitest и Playwright проверяют формат отчёта, сопоставление состояния с IndexedDB, отсутствие утечек в JSON и намеренный статус всех `hardwareAcceptance=NOT TESTED`.
- Приложение не умеет доказать, что запущена настоящая модель, а не `mockRuntime.ts`; аппаратный gate не становится PASS из-за совпадения 35 окон или правильных таймингов.
- Журнал событий содержит максимум 256 записей. Отсутствие события GPU loss не доказывает, что оно не происходило; старые события могли быть вытеснены.
- Значение `navigator.onLine` — подсказка браузера; не доказательство отсутствия обращений в сеть.
- Встроенная оценка JS heap не включает все потоки, память ONNX/WASM, RAM браузерного процесса и VRAM; аппаратный отчёт не выдумывает эти показатели.
- Репозиторий и GitHub Actions не имеют доступа к файлам вашего устройства и к реальному WebGPU браузера пользователя.

## 6. Публикация и откат

PR-30 основан на PR-29 и далее на PR-21–28. Сливать последовательно в порядке зависимостей, выполнить полный CI на `main`, затем испытать реальный браузер. После миграции IndexedDB до v2 **откат на сборку, открывающую базу только с версией 1, невозможен без специальной совместимости**. Не удалять данные браузера при откате без резервного копирования результатов.
